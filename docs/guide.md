# Руководство BarkOdd

[← Главная страница](../README.md) · [Запуск и команды Make](running.md)

Домашнее наблюдение за собакой: один self-hosted сервер, несколько камер и хозяев в общей комнате, просмотр из браузера на телефоне. Без установки мобильного приложения. При запуске можно выбрать общий кабинет без входа, вход по коду или отдельные пользовательские аккаунты.

## Быстрый запуск на компьютере

Нужен Go 1.23 или новее. Для локального запуска без входа:

```sh
AUTH_MODE=none go run ./cmd/barkodd
```

Откройте **http://127.0.0.1:8080**. Создайте комнату и выберите «Устройство питомца»,
затем включите наблюдение и разрешите камеру/микрофон. Для просмотра откройте QR-ссылку
на другом устройстве либо выберите просмотр комнаты в кабинете.

В `none` любой посетитель адреса получает управление общим кабинетом. Для входа
по коду сгенерируйте секрет командой `openssl rand -hex 32`, сохраните его
и передайте через `ADMIN_CODE`:

```sh
AUTH_MODE=admin_code ADMIN_CODE='вставьте-сгенерированный-код' go run ./cmd/barkodd
```

Для нескольких пользователей:

```sh
AUTH_MODE=multi_user ADMIN_CODE='вставьте-сгенерированный-код' go run ./cmd/barkodd
```

**Локальная ссылка с `127.0.0.1`/`localhost` работает только на том же компьютере.** Чтобы уйти из дома и смотреть с телефона, нужен публичный HTTPS-адрес сервера с поддержкой WebSocket. Подготовленный вариант размещения описан ниже. Сам факт локального запуска не делает приложение доступным через интернет.

Бинарник включает webUI; Node.js нужен только для тестов разработки:

```sh
go build -o bin/barkodd ./cmd/barkodd
AUTH_MODE=none ./bin/barkodd
```

## Режимы входа

| `AUTH_MODE` | Поведение |
|---|---|
| `none` | Один общий владелец без входа. Несколько комнат и устройств. |
| `admin_code` (по умолчанию) | Вход в общий кабинет по `ADMIN_CODE`. |
| `multi_user` | Самостоятельная регистрация по логину/паролю; видны свои комнаты и комнаты, куда пользователя добавили хозяином. Админ входит отдельно по `ADMIN_CODE`. |

В multi_user регистрация открыта любому посетителю без приглашений и одобрения.
Логин: 3–32 латинские буквы, цифры, `_`, `.` или `-`, без различия регистра;
`admin` зарезервирован. Пароль: 12–128 символов. После регистрации кабинет открывается
сразу. Админ видит список пользователей и блокирует/разблокирует их. Доступа к
чужим камерам, фотографиям и истории через админку нет. Задавать или сбрасывать
чужие пароли администратор не может, чтобы исключить вход от имени пользователя.
Пользователь может сменить свой пароль с подтверждением текущего.
Регистрации в других режимах нет.

Вход действует 30 дней в этом браузере; перезапуск сервера требует войти снова.
Выход завершает текущую сессию и её камеру, смена пароля — все сессии пользователя.
Блокировка прекращает доступ и камеры заблокированного аккаунта, сохраняя данные.
Камеры других хозяев продолжают работу. Гостевые ссылки действуют, пока в комнате
есть хотя бы один незаблокированный хозяин. Разблокировка требует нового входа
владельца. Пароли и админский код не сохраняются в браузерном хранилище;
сессия передаётся через HttpOnly cookie, пароли на сервере хешируются Argon2id.

QR-ссылка позволяет смотреть одну камеру без регистрации и входа во всех режимах.
В новом браузере владелец видит свои комнаты после входа, но прежний ключ QR
восстановить нельзя: сервер хранит его хеш. Кнопка создания новой ссылки явно
отзывает предыдущую. Само открытие комнаты ссылки не меняет.

## Как пользоваться

### Общая комната и несколько камер

Создайте комнату, например «Дом Бруно»: вместе с ней появляется первая камера.
В кабинете у комнаты есть список камер и форма добавления камеры. Назовите новые
камеры, например «Гостиная» и «Кухня», и на каждом устройстве откройте нужную
камеру кнопкой **«Устройство питомца»**. Включите наблюдение на каждом устройстве.
Несколько камер работают одновременно; запуск новой сессии той же камеры заменяет
её прежний источник. Одна открытая вкладка источника обслуживает одну камеру.

В режиме `multi_user` второй хозяин сначала регистрируется, затем любой хозяин
комнаты добавляет его по логину через **«Добавить хозяина»**. Комната появится
в кабинете добавленного пользователя после обновления списка. Все хозяева имеют
одинаковые права: управляют камерами, настройками, историей и составом хозяев.
Один аккаунт может быть хозяином нескольких комнат. Последнего хозяина удалить нельзя.

В просмотре хозяин выбирает камеру комнаты; одновременно воспроизводится одна
камера. У каждой камеры отдельные настройки, события и фотографии. Остановка,
перезапуск или удаление камеры не затрагивают остальные камеры. Удаление всей
комнаты удаляет все её камеры и историю после подтверждения.

Удаление хозяина сразу прекращает его доступ через аккаунт и наблюдение с его
устройств в этой комнате. Уже известные ему гостевые ссылки остаются отдельным
доступом только для просмотра: при необходимости выпустите новые ссылки камер.
Гость по QR видит только камеру из ссылки, без списка остальных камер и управления.

### Запуск и просмотр

1. На ноутбуке откройте приложение по HTTPS-адресу сервера войдите при необходимости и откройте свою комнату как **«Устройство питомца»**. Выберите камеру/микрофон, начните наблюдение.
2. Телефоном отсканируйте QR. Откроется роль человека с доступом только к камере из ссылки. Сохраните ссылку или вкладку перед уходом.
3. На странице просмотра независимо включайте **«Видео»** и **«Звук»**: можно только слушать, только смотреть или включить оба канала. В режиме «только звук» видео зрителю не передаётся. Выключение обоих каналов сохраняет обнаружение шума и фотографии. Выбор отдельный для каждого зрителя; при переключении соединение ненадолго обновляется. Если браузер приостановил звук, нажмите **«Воспроизвести звук»**.
4. В истории показываются время шума и время фотографии. При обрыве связи последний снимок остаётся доступен, но статус указывает, что данные больше не поступают.
5. **«Остановить наблюдение»** на ноутбуке освобождает камеру и микрофон. Повторный запуск начинает новую историю этой камеры: её прежние события и фотографии удаляются. Остальные камеры комнаты продолжают работу. Остановка сохраняет историю до следующего запуска; временная пауза микрофона или переподключение её не очищают. Перевыпуск ссылки отзывает прежний ключ просмотра этой камеры.

На телефоне или планшете в поле **«Камера»** можно выбрать **«Задняя камера»** или **«Фронтальная камера»**, даже если браузер показывает в списке устройств только одну камеру. Чтобы переключиться, остановите наблюдение, выберите камеру и включите наблюдение снова. Если выбранной камеры нет или браузер не даёт к ней доступ, выберите другую либо «Камера по умолчанию».

Первый источник рассчитан на **ноутбук, подключённый к питанию, с открытой вкладкой и отключённым сном**. Блокировка экрана/закрытие крышки/заморозка вкладки могут остановить наблюдение. Запрос browser Wake Lock — только дополнительная помощь, не гарантия работы при закрытии крышки. Работа источника на заблокированном телефоне не обещается.

Если на iPhone статус звука активен, но ничего не слышно, увеличьте громкость во время прослушивания и проверьте, не выбран ли вывод в наушники или AirPlay. В Safari беззвучный режим может заглушать Web Audio при работающем соединении: для проверки выключите его. BarkOdd запрашивает режим медиавоспроизведения через Audio Session API, когда браузер его поддерживает; после выключения звука возвращает прежний режим. Это поведение iOS описано [разработчиками WebKit](https://bugs.webkit.org/show_bug.cgi?id=237322#c6). После обновления приложения перезагрузите обе вкладки и включите звук снова.

## Что считается событием

Это детектор громкости, **не распознавание именно лая**. Речь, музыка и хлопки тоже могут вызвать событие. Чувствительность влияет только на события и фотографии: она не усиливает и не отключает живой звук у зрителя.

Чтобы подобрать чувствительность под комнату:

1. Оставьте устройство на обычном месте и включите наблюдение.
2. Нажмите **«Откалибровать фон»**. В течение **5 секунд** оставьте обычный фоновый шум без разговоров и звуков питомца, держите вкладку открытой. Камера и трансляция продолжают работать; новые шумовые события во время замера не создаются.
3. После замера появится предложенный порог. Ползунок **«Точная настройка»** позволяет сдвинуть его к **«Больше звуков»** (ниже порог) или **«Меньше срабатываний»** (выше порог).
4. Нажмите **«Сохранить настройки»** — только после этого новый порог начнёт действовать. Наблюдение перезапускать не нужно. Точный порог сохранится после перезагрузки страницы и сервера.
5. Проверьте обычный фон, затем произнесите фразу или воспроизведите нужный звук с места, где обычно находится питомец. Фон не должен постоянно обновлять «Последний шум», а нужный звук должен его обновлять. При необходимости поправьте порог и сохраните ещё раз.

Шкала показывает точный уровень даже ниже 1%. **Сплошная отметка** — действующий порог, **пунктирная** — несохранённая поправка. При превышении действующего порога полоса меняет цвет. Проценты показывают цифровой уровень микрофона, а не физическую громкость в комнате; положение на шкале логарифмическое, чтобы тихие звуки было проще различать.

Замер можно отменить. Остановка наблюдения, потеря микрофона или скрытие вкладки прерывают калибровку без изменения порога. Если микрофон передаёт только нули, замеров недостаточно или фон слишком громкий, появится объяснение; предыдущие настройки сохранятся. После смены микрофона, перемещения устройства или заметного изменения фона повторите калибровку. Она учитывает громкость, поэтому не различит лай и фон одинакового уровня.

- Готовые режимы остаются: «Только очень громкие», «Громкие», «Обычные», «Тихие», «Даже очень тихие». Их пороги RMS — 0.1, 0.03, 0.01, 0.003 и 0.0005. Для результата калибровки или ручной поправки между режимами отображается **«Свой порог»**.
- В новых комнатах выбран режим «Обычные» (0.01). Шум должен длиться хотя бы 150 мс. На максимальной чувствительности может фиксироваться и фон комнаты. Несколько звуков могут дополнять одну карточку, поэтому ориентируйтесь также на время последнего шума.
- После окончания выбранного интервала следующий подтверждённый звук начинает новую карточку, даже если шум не прерывался. До этого звуки дополняют текущую карточку.
- Последний шум обновляется не чаще раза в секунду.
- Камера делает фотографии не чаще раза в 30 секунд, настройка 10–300 секунд. Это минимальное время между снимками, а не расписание: в тишине новые фото не делаются. При продолжающемся шуме очередной снимок получает новую карточку, сохраняя предыдущую фотографию в истории. Если камера недоступна, событие может быть без фото. Неудачная съёмка повторяется при следующем подтверждённом шуме, а отправленный снимок остаётся в очереди до подтверждения сохранения. Интервал рассчитывает только устройство камеры от момента успешной съёмки. Подтверждение сервера и задержки сети его не сдвигают. Сервер сохраняет фото по мере получения; ожидание отправки фото не задерживает новые сведения о шуме. Без связи съёмка продолжается с выбранным интервалом, а последние 12 эпизодов остаются в памяти страницы для отправки после подключения (не дольше 24 часов). Начало карточки, время последнего звука и время снимка показываются отдельно и могут различаться.
- Кнопка «Очистить историю» доступна владельцу комнаты и удаляет события и фотографии после подтверждения. Наблюдение продолжает работать; первый новый шум получает свежий снимок, если камера доступна, без ожидания интервала от удалённого фото. Затем снова действует выбранный интервал. Гостям кнопка недоступна.
- При каждом новом запуске наблюдения история этой камеры очищается автоматически. Остановка, повторное подключение и перезапуск сервера с той же сессией камеры историю сохраняют. Дополнительно история ограничена 200 эпизодами и 7 днями на камеру. Видео не записывается.
- На мобильном экране последний снимок находится сверху, перед камерой и историей.
- Обновления работают при открытой странице просмотра; push-уведомления при закрытом браузере не реализованы.

## Выбор режима видео

Режим выбирается **на сервере**, одинаков для всех комнат. В `.env` укажите один вариант:

```dotenv
MEDIA_TRANSPORT=websocket
# либо:
# MEDIA_TRANSPORT=webrtc
```

После изменения перезапустите приложение командой Compose из раздела размещения. При запуске бинарника передайте переменную окружения, например `AUTH_MODE=none MEDIA_TRANSPORT=webrtc go run ./cmd/barkodd`. Браузеры узнают режим автоматически при подключении; комнаты, ключи, QR и история сохраняются. После перезапуска в защищённых режимах нужно снова войти и включить наблюдение: сессии входа хранятся в памяти сервера. В открытом режиме клиент переподключается автоматически. Автоматического перехода между транспортами нет; неизвестное значение останавливает запуск с ошибкой.

| Режим | Видео и звук | Размещение |
|---|---|---|
| `websocket` — по умолчанию | JPEG до 5 кадров/с и звук PCM через сервер; больше трафика | HTTPS/WSS, без TURN и дополнительных портов для видео |
| `webrtc` | Выбранные видео- и аудиодорожки между браузерами или через TURN; обычно экономнее | HTTPS/WSS для управления; STUN и доступный извне TURN для сетей, где прямое соединение невозможно |

В обоих режимах есть **прямой звук по нажатию зрителя**. Ссылка просмотра даёт доступ и к видео, и к звуку. Канал передаётся только тем зрителям, которые его включили; без подписчиков он не отправляется. Видео и звук не записываются, шумовые фотографии сохраняются отдельно. При пропадании кадров изображение скрывается, а работающий звук продолжает воспроизводиться. При остановке просмотра соединение и аудиобуфер освобождаются. Микрофон на телефоне зрителя не запрашивается. На устройстве питомца камера продолжает работать для снимков даже при прослушивании без видео.

WebSocket: длинная сторона кадра до 960 px, лимит 200 КиБ; при медленной сети остаётся последний кадр. Звук — mono PCM16, 16 кГц, пакеты по 100 мс (около 32 КБ/с без учёта служебных данных). При отставании старое аудио отбрасывается; запись не накапливается. Для передачи звука нужен браузер с AudioWorklet; при его отсутствии видео и детектор продолжают работать, а источник показывает ошибку звука. HTTPS/WSS шифрует путь до сервера, который видит JPEG и аудиопакеты в открытом виде; сквозного шифрования между браузерами нет.

WebRTC: служебный WebSocket используется для авторизации, согласования и отзыва доступа; видео и звук идут через WebRTC. При отзыве ссылки источник закрывает peer зрителя. При потере служебного соединения или отсутствии подтверждения сервера 6 с источник закрывает все peer-соединения, даже если прямой медиаканал ещё работал.

### STUN/TURN для WebRTC

Пустой `STUN_URLS` включает `stun:stun.l.google.com:19302`; свои адреса задаются через запятую. `STUN_URLS=none` отключает STUN, например для локальной проверки. STUN не пересылает видео и не заменяет TURN.

Для **уже доступного TURN-сервера**:

```dotenv
MEDIA_TRANSPORT=webrtc
TURN_URLS=turn:relay.example.com:3478?transport=udp,turn:relay.example.com:3478?transport=tcp
TURN_SECRET=<shared-secret-сервера-TURN>
```

При shared secret BarkOdd выдаёт авторизованным клиентам временные credentials на 1 час; исходный secret браузеру не отправляется. Соединение с TURN автоматически обновляется каждые 45 минут, чтобы постоянно работающая вкладка получала свежие credentials; просмотр может ненадолго прерваться. Альтернатива — `TURN_USERNAME` и `TURN_PASSWORD` вместо `TURN_SECRET`. Не задавайте оба способа одновременно. WebSocket-режим не использует ICE-настройки.

Сам TURN запускается отдельно. Для self-hosted варианта подходит [coturn с официальной инструкцией Docker](https://github.com/coturn/coturn/blob/master/docker/coturn/README.md). Его `use-auth-secret`/`static-auth-secret` должны соответствовать `TURN_SECRET`; настройте public IP и доступные порты самого TURN и relay-диапазона. Если сервер за роутером, эти порты нужно пробросить. Caddy-маршрут приложения не заменяет TURN.

Без TURN WebRTC может работать локально и в части сетей, но просмотр через мобильного оператора не гарантируется. Наличие URL/credentials в `.env` не подтверждает доступность TURN: перед уходом проверьте оба устройства через разные сети.

## Размещение для просмотра вне дома

В `compose.yaml` два сервиса: приложение и Caddy для HTTPS/WSS. Сервер/VPS не создаётся автоматически.

1. На своём сервере установите Docker с Compose и перенесите проект.
2. Выполните `make init`, задайте `AUTH_MODE` и укажите `APP_HOST` в `.env` — публичное имя, направленное на сервер. Команда создаёт случайный `ADMIN_CODE` только для нового файла; в существующем файле заполните код вручную. Для этого варианта `PUBLIC_URL` формируется из `APP_HOST` автоматически.
3. Разрешите TCP **80 и 443**. UDP 443 используется только для необязательного HTTP/3, для просмотра не нужен.
4. Запустите:

```sh
docker compose up -d --build
docker compose logs --tail=50 app https
```

Откройте `https://<APP_HOST>` на устройстве питомца, разрешите камеру/микрофон и отсканируйте QR телефоном. Оба клиента обращаются к тому же HTTPS-серверу. В режиме WebSocket дополнительные пробросы портов для видео не нужны. Для WebRTC учитывайте настройки отдельного TURN выше. Перед уходом проверьте просмотр с отключённым Wi-Fi на телефоне.

Если перед приложением другой reverse proxy, он должен поддерживать WebSocket upgrade и длительные соединения; Caddy делает это автоматически. Не буферизуйте WebSocket и не ставьте короткий общий timeout на этот маршрут.

**Без собственного домена:** можно использовать `TLS_CERT_FILE` и `TLS_KEY_FILE` с доверенным браузером сертификатом для публичного IP/адреса. HTTP по внешнему IP недостаточно для камеры; Compose-шаблон автоматизирует вариант с DNS-именем. Вход и регистрация зависят от `AUTH_MODE`; первоначальная настройка сервера остаётся задачей владельца.

## Размещение за существующим Caddy на Mac mini

В каталоге проекта заполните `.env`. Подставьте свой домен и сгенерируйте код доступа. Для установки в подпути укажите полный `PUBLIC_URL` с завершающим `/`.

```dotenv
PUBLIC_URL=https://dog.example.com/barkodd/
AUTH_MODE=admin_code
ADMIN_CODE=<случайный-код-администратора>
```

Подключите Caddy и приложение к общей Docker-сети. Для подпути `/barkodd/` добавьте к своему сайту маршрут:

```caddy
redir /barkodd /barkodd/ 308
handle_path /barkodd/* {
    reverse_proxy barkodd-app:8080
}
```

Caddy снимает префикс перед передачей запроса приложению. Из каталога проекта запустите приложение и проверьте публичный маршрут, подставив свой домен:

```sh
docker compose -f deploy/compose.macmini.example.yaml --env-file .env up -d --build
curl -fsS https://dog.example.com/barkodd/healthz
```

Комнаты и снимки хранятся в постоянном томе. Для работы WebRTC через TURN задайте параметры своего relay-сервера в `.env` и проверьте передачу видео между устройствами в разных сетях.

## Конфигурация бинарника

| Переменная | Значение |
|---|---|
| `AUTH_MODE` | `none`, `admin_code` (по умолчанию) или `multi_user`. Смена через перезапуск. |
| `ADMIN_CODE` | Код владельца/админа, 32–128 символов `A-Z a-z 0-9 _ -`. Обязателен в защищённых режимах. |
| `ROOM_CREATION_KEY` | Прежнее имя `ADMIN_CODE`. Если заданы оба, должны совпадать. |
| `MEDIA_TRANSPORT` | `websocket` (default) или `webrtc`. Общее для всех комнат; смена через перезапуск. |
| `STUN_URLS` | STUN URL через запятую; пусто — публичный default, `none` — отключить. Только WebRTC. |
| `TURN_URLS` | TURN/TURNS URL через запятую. Только WebRTC. |
| `TURN_SECRET` | Shared secret TURN для временных credentials. |
| `TURN_USERNAME`, `TURN_PASSWORD` | Статическая пара вместо shared secret. |
| `ADDR` | Адрес HTTP listener, по умолчанию `127.0.0.1:8080`. В контейнере `0.0.0.0:8080`. |
| `DATA_DIR` | Каталог данных, по умолчанию `data`. Один процесс на каталог. |
| `PUBLIC_URL` | Полный публичный адрес, включая подпуть: используется для ссылок/QR, проверки Origin и параметров cookie. Для подпути прокси обязан снять префикс; сам Go-сервер обслуживает корень. При локальном прямом запуске оставьте пустым. |
| `TLS_CERT_FILE`, `TLS_KEY_FILE` | Необязательная пара PEM-файлов для HTTPS без reverse proxy. |

## Обновление и существующие комнаты

Существующий `ROOM_CREATION_KEY` продолжает работать как админский код.
Без корректного кода защищённый режим теперь завершается ошибкой запуска.
Открытый режим включается только явно: `AUTH_MODE=none`.

При переходе на общие комнаты каждая существующая комната становится комнатой
с одной камерой и прежним хозяином. Идентификатор камеры, гостевые ссылки,
настройки, фотографии и история сохраняются. Состав хозяев хранится в `DATA_DIR/groups/`;
в резервную копию включайте весь `DATA_DIR`.

Комнаты без прежней привязки к аккаунту получает общий
владелец, в multi_user — администратор. Новый зарегистрированный пользователь
получает пустой кабинет. Старый ключ камеры больше не заменяет вход: после
обновления перезагрузите вкладки и войдите в защищённых режимах.

`none` и `admin_code` используют один кабинет. Переход в multi_user сохраняет его
за админом. Обратный переход запрещён, пока в хранилище есть обычные пользователи
или их комнаты: частные данные не объединяются в общий кабинет. Для отдельного
однопользовательского экземпляра задайте новый `DATA_DIR`.

При WebRTC с TURN владелец один раз подтверждает старую неподтверждённую комнату
на устройстве питомца. До этого она получает только STUN. Новые комнаты разрешены
правилами выбранного режима, включая комнаты самостоятельно зарегистрированных
пользователей в multi_user.

Уже выданные TURN-реквизиты код приложения не отзывает. При обновлении публичного сервера смените ранее использовавшуюся статическую пару TURN; если требуется немедленно прекратить ранее выданный доступ, смените shared secret на TURN и в приложении и завершите старые TURN-сессии средствами самого TURN. Эти действия выполняются отдельно на сервере.

## Данные и доступ

Комнаты привязаны к списку хозяев на сервере; управление требует входа (кроме явно
открытого режима). Ключ просмотра из QR — доступ к одной камере и её истории:
делитесь ссылкой только с тем, кому он нужен. Фрагмент ссылки не отправляется
HTTP-серверу; API получает гостевой ключ в `Authorization`, WebSocket — в первом
сообщении. При ручном вызове изменяющего API передавайте точный `Origin` приложения;
WebSocket не принимает ключи ни в URL, ни в заголовке `Authorization`.

Данные пользователей находятся в `DATA_DIR/auth/`, общие комнаты и их хозяева —
в `DATA_DIR/groups/`, записи отдельных камер — в корне каталога.
Резервная копия должна включать весь каталог. Гостевые привязки и сохранённые
QR-ключи остаются в браузере, пароли и код администратора — нет. Очистка браузера
не лишает зарегистрированного владельца доступа к своим комнатам после нового входа.

История и фотографии находятся на вашем сервере. Диск не шифруется приложением; защищайте хост и резервные копии. Кадры и запросы защищены HTTPS/WSS при удалённом размещении. В режиме WebSocket видео проходит через Go-сервер; WebRTC использует прямое соединение либо отдельный TURN. События и фото в обоих режимах находятся на сервере.

Для резервной копии остановите сервер и скопируйте весь `DATA_DIR` (в Compose — volume `barkodd_data`). После восстановления старые ссылки работают при сохранении камер и ключей. На устройстве питомца кнопка «Удалить камеру» с подтверждением удаляет её историю и фотографии, отзывает подключения и освобождает место. Кнопка «Удалить комнату» в кабинете удаляет все её камеры. При ошибке очистки файлов доступ уже закрыт, а сервер повторяет очистку при запуске и раз в минуту. Не прерывайте резервное копирование каталога: файлы `.deleted`, в том числе в `groups/`, нужны для завершения прерванного удаления. Удаление volume удаляет все данные. Не запускайте несколько экземпляров приложения на одном каталоге.

Сервер предназначен для небольшого личного использования: до 100 камер и 1000 общих комнат на весь сервер, число аккаунтов — 1000. В multi_user создание комнат доступно каждому зарегистрированному пользователю. До 6 активных зрителей на камеру. Частота событий ограничена двумя в секунду с коротким запасом из трёх; одновременно обрабатывается одно событие камеры и до четырёх фотографий сервера. Вход ограничен 100 попытками в минуту на сервер, 30 на операцию и IP (регистрация — 5), 10 на логин; за reverse proxy общий адрес может разделяться пользователями. Одновременно вычисляются не более двух хешей пароля. До 32 сессий на пользователя и 4096 на сервер. Для большой аудитории потребуются отдельные пользовательские квоты и другое хранилище.

## Проверки разработки

```sh
go test -race ./...
go vet ./...
npm ci
npm test
```

Для браузерной проверки нужен Node.js 20+ и Chromium/Google Chrome. Playwright использует тестовую камеру и микрофон, не личные устройства. В WebSocket-тесте `RTCPeerConnection` намеренно отсутствует; WebRTC-тест проверяет настоящий peer между браузерными контекстами и отзыв доступа со стороны источника. Аудиотесты в обоих режимах измеряют реальный сигнал воспроизведения, проверяют выбор каналов, отсутствие видео при прослушивании, восстановление звука и отзыв доступа. Запустите отдельный сервер с временными данными и запустите тесты:

```sh
AUTH_MODE=admin_code ADMIN_CODE=test-owner-key-0123456789abcdef0123456789 DATA_DIR=/tmp/barkodd-browser-data ADDR=127.0.0.1:8088 go run ./cmd/barkodd
# В другом терминале:
BARKODD_BASE_URL=http://127.0.0.1:8088 npm run test:browser
```

Если Chrome не установлен, выполните `npx playwright install chromium`; тесты используют `BARKODD_CHROME_PATH`, когда он задан. Тестовые комнаты сохраняются только в выделенном `DATA_DIR`.

Для проверки размещения под `/barkodd/` запустите тестовый сервер с `PUBLIC_URL=http://127.0.0.1:8089/barkodd/` на том же порту 8088, затем:

```sh
node tests/subpath-proxy.mjs
# В другом терминале:
BARKODD_BASE_URL=http://127.0.0.1:8089/barkodd/ npm run test:browser
```

Тестовый proxy снимает префикс и передаёт HTTP/WebSocket, как маршрут Caddy.

Для второго прогона перезапустите тестовый сервер с `MEDIA_TRANSPORT=webrtc STUN_URLS=none` и выполните те же браузерные тесты с `BARKODD_TRANSPORT=webrtc`. Без этой переменной тесты ожидают WebSocket по умолчанию. Локальный RTC-прогон не доказывает доступность внешнего TURN или мобильной сети.

Проверка звука в движке Safari: `BARKODD_BROWSER=webkit npm run test:browser -- tests/audio.spec.js` (нужен установленный WebKit Playwright). Этот сценарий подставляет синтетические камеру и микрофон, измеряет выходной аудиосигнал и проверяет режим Audio Session, если API доступен. Для WebRTC добавьте `BARKODD_TRANSPORT=webrtc` и адрес соответствующего тестового сервера. Chromium также проверяется без отключения штатных ограничений автозапуска. Эти тесты не воспроизводят физический беззвучный переключатель iPhone: его нужно проверить на устройстве.

Если два локальных контекста WebKit без STUN не соединяются по mDNS, для этого теста можно добавить `BARKODD_LOCAL_ICE=1`: только на localhost тестовый получатель заменит имя `.local` в ICE-кандидате на `127.0.0.1`. Так проверяются реальные передача и воспроизведение аудио, но не обнаружение адресов в сети. Запускайте аудиосценарии браузеров последовательно: режим медиавоспроизведения может прервать звук другого браузера.

Документация: [WebSocket](https://developer.mozilla.org/en-US/docs/Web/API/WebSockets_API), [доступ к камере](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [Caddy reverse proxy](https://caddyserver.com/docs/caddyfile/directives/reverse_proxy).


Сценарии авторизации находятся в `tests/auth.spec.js`. Для полного прогона запустите
отдельные серверы с временными каталогами для каждого режима и задайте тестам
`BARKODD_AUTH_MODE=none`, `admin_code` или `multi_user` соответственно.
`BARKODD_OWNER_KEY` задаёт тестовый админский код; по умолчанию используется значение
из примера выше. Для основного медиасценария и микрофона достаточно `admin_code`.


Сценарий общих хозяев и камер находится в `tests/shared-rooms.spec.js` и работает
с `BARKODD_AUTH_MODE=multi_user`. Он проверяет два аккаунта, две одновременные
камеры, переключение просмотра и отзыв доступа. Для отдельного повторного прогона
используйте свежий тестовый сервер: быстрые серии регистраций на одном экземпляре
могут достичь штатного ограничения 5 регистраций в минуту на IP.
