# Режимы авторизации BarkOdd

Статус: согласовано пользователем 2026-11-06. Реализованы все три режима, самостоятельная регистрация и гостевой просмотр по QR. Проверки записаны в плане реализации.

## Запрос и границы

При запуске одного бинарника или Compose выбрать один из трёх режимов:
без авторизации для одного пользователя; вход по админскому коду для одного
пользователя; несколько пользователей и администратор.

Предложение исполнителя: «один пользователь» означает одного общего владельца,
у которого может быть несколько комнат и устройств. Роли камеры и зрителя
остаются отдельными от роли пользователя или администратора.

Для multi-user пользователь выбрал самостоятельную регистрацию по логину и паролю.
Регистрация открыта любому посетителю, без приглашения и одобрения администратора.
Email, OAuth, восстановление пароля по почте и внешняя база данных в объём
не входят. Работа касается репозитория, без изменения рабочего сервера.

## Подходы

1. Встроенные пользователи и серверные сессии поверх существующих комнат —
   предложение исполнителя с выбранной пользователем самостоятельной регистрацией.
   Один бинарник, привычный запуск,
   разделение комнат между пользователями, доступ с нового устройства.
2. Индивидуальные коды вместо логина и пароля — проще выдавать, но нет привычной
   учётной записи и смены своего пароля. Пользователь выбрал логин/пароль
   и самостоятельную регистрацию вместо индивидуальных кодов и создания админом.
3. Внешний провайдер входа — дополнительные компоненты и настройка для домашнего
   сервера; для запрошенных режимов не предлагается.

## Конфигурация

- `AUTH_MODE=none|admin_code|multi_user`, по умолчанию `admin_code`.
- `ADMIN_CODE` — секрет владельца/администратора в двух защищённых режимах.
  Формат сохраняет требования нынешнего ключа: 32–128 символов `A-Z a-z 0-9 _ -`.
- `ROOM_CREATION_KEY` поддерживается как прежнее имя `ADMIN_CODE`. Если заданы
  оба и отличаются, запуск завершается понятной ошибкой.
- Неизвестный режим или отсутствие корректного кода в защищённом режиме — ошибка
  запуска. Пустой код не включает открытый режим. Это намеренно меняет старое
  поведение, когда без ключа сервер запускался, но запрещал создание комнат.
- В `none` код не требуется. Любой посетитель адреса получает права общего
  владельца. Это явно описывается рядом с настройкой в README и `.env.example`.
- Режим выбирается только при запуске; публичный API сообщает его интерфейсу,
  но не возвращает секреты.

## Поведение режимов

| Режим | Вход | Комнаты | Управление пользователями |
|---|---|---|---|
| `none` | Сразу общий кабинет | Все комнаты общего владельца | Отсутствует |
| `admin_code` | Админский код | Тот же общий кабинет | Отсутствует |
| `multi_user` | Регистрация и вход по логину/паролю; отдельный вход админа по коду | Только свои комнаты | Только админ |

Кабинет показывает список комнат, создание комнаты и выбор устройства для
существующей комнаты. Вход с другого браузера возвращает доступ к своим комнатам.
Выбор роли камеры не включает камеру или микрофон без обычного действия пользователя.

В `multi_user` на экране входа доступна регистрация: логин, пароль и подтверждение
пароля. После успешной регистрации пользователь сразу входит в пустой собственный
кабинет и может создавать комнаты. Регистрация всегда создаёт обычного пользователя;
передать административную роль через запрос нельзя. Существующие комнаты общего
владельца новому пользователю не передаются.

Логины уникальны без учёта регистра; нормализация, допустимые символы и ограничения
длины одинаковы при регистрации и входе. Имя `admin` зарезервировано. Пароль
содержит не менее 12 символов, верхний предел выбирается вместе с алгоритмом хеширования
без молчаливого усечения. При одновременной регистрации одинакового логина создаётся
только одна учётная запись. В `none` и `admin_code` регистрация отсутствует и в UI,
и в API.

Администратор сбрасывает пользователям пароль и блокирует/разблокирует учётные
записи. Пользователь может изменить свой пароль, подтвердив текущий.
Администратор может создавать собственные комнаты, но не получает автоматического
доступа к видео, фотографиям или истории других пользователей. Удаление пользователей
и передача комнат между пользователями в первую реализацию не входят.

Смена/сброс пароля отзывает сессии пользователя; смена своего пароля возвращает
его на вход. Блокировка дополнительно закрывает доступ по гостевым ссылкам его
комнат и прекращает активные подключения. Данные сохраняются; разблокировка
возвращает действие прежних гостевых ссылок.

Пример навигации:

```text
none:       Мои комнаты → Комната → Устройство питомца / Просмотр
admin_code: Ввод кода → Мои комнаты → Комната
multi_user: Регистрация / Вход → Мои комнаты → Комната
            Вход администратора → Мои комнаты / Пользователи
QR-ссылка:  Просмотр одной комнаты
```

## Авторизация комнат и гостевые ссылки

Каждая комната получает стабильный `ownerId`. В защищённых режимах действия
владельца требуют действующей сессии соответствующего владельца. Старый host token
сам по себе больше не даёт управление, в том числе если его предъявил другой
авторизованный пользователь. В `none` действует неявный общий владелец.

Владелец может смотреть свои комнаты через сессию без гостевого ключа. Просмотр
по QR/ссылке остаётся доступен без входа во всех режимах, только для одной комнаты,
пока ссылка не отозвана и её владелец не заблокирован. Гостевой ключ не даёт
список комнат, управление, создание, публикацию кадров или настройки пользователей.

Сервер хранит только хеши ключей, поэтому открыть комнату на новом устройстве
не означает восстановить прежнюю QR-ссылку. Если действующий viewer token сохранён
в браузере, можно показать прежнюю ссылку. Иначе показывается явное действие
«Создать новую ссылку», предупреждающее об отзыве предыдущей. Открытие комнаты
само по себе ссылки не перевыпускает.

Общая политика доступа применяется ко всем трём путям: обычному HTTP API,
загрузке событий/фотографий и авторизации/дальнейшей работе WebSocket. После
декодирования фотографии повторно проверяются сессия, владелец и активный источник.
Выход, истечение сессии и сброс пароля прекращают операции и подключения этой
сессии; блокировка владельца прекращает все подключения его комнат. Проверки
применяются к обоим медиатранспортам.

## Сессии и хранение

Непрозрачные случайные сессии хранятся на сервере, браузеру передаётся HttpOnly
cookie с SameSite и Secure для HTTPS. Cookie учитывает PUBLIC_URL и подпуть.
Срок сессии — 30 дней; перезапуск сервера требует повторного входа. Выход закрывает
только текущую сессию. Пароли и админский код не сохраняются в localStorage.

Изменяющие запросы с cookie и запросы открытого режима защищаются от межсайтовой
отправки; WebSocket сохраняет строгую проверку Origin. Вход и регистрация получают
ограничение частоты попыток и ограничение параллельных дорогих операций с паролем.
Число учётных записей ограничено 1000, существующий общий предел 100 комнат
сохраняется. Регистрация не обходит ограничения сервера. Пароли хранятся
как salted hash проверенной библиотеки; конкретный алгоритм и параметры выбирает
исполнитель по актуальной документации. Проверка пароля не держит общий mutex комнат.

Учётные записи и версия схемы хранятся отдельно в `DATA_DIR/auth/`: корневые
`*.json` сейчас считаются комнатами. Запись атомарная, права файлов закрытые,
идентификаторы пользователей неизменяемые. Секретные данные не попадают в API
списков, сообщения об ошибках или логи.

## Существующие данные и смена режима

Старые комнаты без ownerId принадлежат стабильному общему владельцу. В multi-user
этот владелец становится администратором; комнаты не присваиваются первому
вошедшему пользователю. ID, события, фотографии, хеши гостевых ключей и версии
ссылок сохраняются. Подтверждение старых комнат для TURN остаётся явным действием
владельца; для новых комнат разрешение следует из действующей политики режима.

`none` и `admin_code` используют одного владельца; переключение сохраняет комнаты.
При переходе в multi-user общий владелец становится администратором. Обратный
переход запрещён при наличии пользовательских учётных записей или комнат с другими
владельцами: существующие частные комнаты не становятся общими молча. Для отдельного
однопользовательского экземпляра можно указать новый DATA_DIR. Смена режима не
удаляет данные автоматически.

После обновления старые камеры должны войти заново в защищённых режимах; старые
гостевые ссылки сохраняются. Действующие TURN-реквизиты не отзываются самим
приложением; существующая модель остановки WebRTC через служебное соединение
сохраняется.

## Проверка реализации

- Конфигурация трёх режимов, ошибочные значения и совместимость имени ключа.
- Список комнат, создание, повторный вход с нового браузера и изоляция пользователей.
- Самостоятельная регистрация, уникальность логина при конкурентных запросах,
  проверка пароля, лимиты и запрет регистрации вне multi-user.
- Регистрация не выдаёт административную роль и не присваивает старые комнаты.
- Вход/выход, сброс пароля, блокировка, истечение сессии и закрытие активных потоков.
- Обходы через старые host tokens, чужие комнаты, события, фото и WebSocket.
- Гостевые QR-ссылки, их отзыв, перезапуск и перенос существующих данных.
- Same-origin защита, ограничения входа и отсутствие секретов в ответах/хранилище браузера.
- Браузерные сценарии трёх режимов, подпуть `/barkodd/`, WebSocket и WebRTC.
- Go race suite, vet, текущие JS-тесты и независимое ревью.

README, `.env.example`, оба Compose-файла и документация поведения обновляются
вместе с кодом. Коммиты разрешены отдельным запросом пользователя от 2026-11-07; публикация не входит в это изменение.
