# Общие комнаты, хозяева и камеры

Пользователь 2026-11-07 выбрал общую комнату с несколькими хозяевами, отдельными
аккаунтами, правом управления и несколькими камерами. Реализация локальная,
без развёртывания. После проверки пользователь отдельно поручил оформить коммиты.

## Поведение

- Комната видна в кабинете каждого её хозяина. Пользователь может участвовать
  в нескольких комнатах; добавление хозяина — по логину существующего аккаунта.
- Все хозяева равноправны: добавляют/удаляют камеры и хозяев, изменяют настройки,
  очищают историю и удаляют комнату. Последнего хозяина удалить нельзя.
- В комнате несколько именованных камер. Источники работают одновременно,
  каждый со своими настройками, сессией и историей. Перезапуск одной камеры
  не очищает историю остальных. Одна вкладка источника обслуживает одну камеру.
- Кабинет показывает комнаты и камеры внутри них; просмотр позволяет выбрать
  камеру. Одновременная сетка видеопотоков в этот объём не входит.
- Гостевые ссылки остаются ссылками просмотра отдельной камеры и не дают
  управление. Существующие URL, фотографии и история сохраняются.
- При удалении хозяина немедленно прекращаются его соединения и публикация
  с его сессий в этой комнате. Остальные хозяева и их камеры продолжают работу.
  Блокировка аккаунта действует так же во всех его комнатах. Гостям комната
  недоступна, если все её хозяева заблокированы.
- В режимах none/admin_code сохраняется общий кабинет; отдельные хозяева
  добавляются только в multi_user. Админ не получает чужие комнаты автоматически.

## Подходы

1. **Общая комната над существующими камерами — выбран исполнителем.**
   Существующая внутренняя room остаётся единицей медиа/истории. Добавляется group
   с участниками, а камеры ссылаются на неё. Это сохраняет проверенные транспорты
   и старые ссылки, ограничивает риск миграции.
2. Несколько источников непосредственно внутри существующей room потребовали
   бы одновременно изменить историю, сигнализацию, оба транспорта и все URL.
3. Отдельные комнаты и общие гостевые ссылки не дают выбранного пользователем
   совместного управления и общего списка камер.

## Контракт реализации

- Группа хранится в `data/groups/<id>.json`: id, name, createdAt, memberIds.
  Камера получает `groupId`. Старая камера мигрирует в отдельную группу со своим
  названием и прежним владельцем; идентификатор камеры и токены сохраняются.
- `GET /api/groups` → `{groups:[{id,name,createdAt,members,cameras}]}`.
  members: `[{id,username,disabled}]`; cameras: `[{id,name,online,monitoring}]`.
- `POST /api/groups {name}` → группа с пустым списком камер (201).
- `GET /api/groups/:id` → та же группа; `DELETE` удаляет её и все камеры.
- `POST /api/groups/:id/members {username}` → обновлённая группа;
  `DELETE /api/groups/:id/members/:userId` → обновлённая группа.
- `POST /api/groups/:id/cameras {name}` → прежний ответ создания камеры
  `{id,ownerId,hostToken,viewerToken,groupId}` (201).
- Старые `/api/rooms` и `/api/rooms/:cameraId/...` сохраняются. Создание через
  старый API создаёт группу с одной камерой. Список включает доступные камеры.
  Состояние камеры дополнено groupId/groupName; имя камеры остаётся name.
- Для HTTP, фото, событий и WebSocket действует единая проверка членства.
  Удаление группы и миграция должны быть безопасны при перезапуске/сбое записи.

## Проверка

Серверные тесты: совместный доступ и его отзыв, независимые камеры/история,
блокировка одного из хозяев, последний хозяин, отсутствие доступа у постороннего
и администратора, прежние ссылки после миграции и перезапуска.
Браузер: два аккаунта, добавление хозяина и второй камеры, одновременные источники,
переключение просмотра, отзыв доступа. Прогнать Go race, JS и браузерные тесты
для websocket/webrtc. Использовать синтетические устройства.
