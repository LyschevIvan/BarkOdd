# BarkOdd — выбор WebSocket или WebRTC

Решение: один self-hosted Go-сервер и один web-клиент с ролями «Устройство питомца» и «Устройство человека». Пользователь поручил реализацию после обсуждения этой схемы. Принятые для первой версии допущения: источник — ноутбук с открытой страницей и отключённым сном; телефон используется для просмотра. Мобильного приложения нет. Режим входа выбирается через AUTH_MODE: none, admin_code или multi_user с самостоятельной регистрацией; подробности в [схеме авторизации](superpowers/specs/2026-11-06-auth-modes-design.md).

## Поведение

- Владелец создаёт комнату из своего кабинета; управление использует сессию из HttpOnly cookie (в none владелец неявный). Гостевой ключ просмотра сохраняется в localStorage отдельно от учётных данных, QR/ссылка передаёт его во фрагменте URL, гостевой HTTP API использует Authorization Bearer.
- Захват камеры и микрофона начинается только по кнопке. Видео передаётся выбранным сервером транспортом только по запросу зрителя; локальная камера остаётся доступна для фотографий при выключенном просмотре.
- Обнаруживается шум, не классифицируется лай. RMS-порог настраивается (по умолчанию 0.06), подтверждение шума 150 мс; новый эпизод требует 5 секунд тишины и завершения интервала от предыдущего начала эпизода или последнего снимка/подтверждения. Последний шум обновляется не чаще раза в секунду; фотография — не чаще раза в 30 секунд, интервал регулируется 10–300 секунд.
- Сервер сохраняет историю и JPEG-фото на диске; максимум 200 событий на комнату и срок 7 дней. При недоступности устройства прежняя история остаётся доступной, статус явно показывает потерю связи. Запись видео и фоновые push-уведомления не входят в первую версию.
- Переподключение использует прежние ключи; повторный QR не нужен. Просмотр можно включить и выключить. Прямой звук не передаётся; микрофон используется для детектора шума. Остановка наблюдения освобождает камеру/микрофон.

## Архитектура и варианты

Выбран принятый пользователем сервер+клиент. Публичный сервер выдаёт HTTPS webUI, хранит события и управляет просмотром. `MEDIA_TRANSPORT=websocket` (по умолчанию) пересылает JPEG по WSS; `MEDIA_TRANSPORT=webrtc` использует кодированное видео между браузерами или через отдельный TURN. Для JPEG STUN/TURN не нужны, сервер видит кадры. Для RTC тот же авторизованный WS передаёт служебные сообщения. Настройка общая для экземпляра; смена требует перезапуска и принимается актуальным клиентом при reconnect.

Go HTTP + JSON-хранилище с атомарной записью, vanilla JS/CSS с embed в бинарник, QR через Go-библиотеку. Для WebSocket используется `github.com/coder/websocket`. REST polling состояния — раз в 2 секунды. Docker/Caddy-шаблоны поддерживают размещение в корне и существующий `/barkodd/` (reverse proxy снимает префикс, `PUBLIC_URL` содержит полный внешний путь). Инструкции обновления сохраняют volume с комнатами и ключами; локальная реализация не означает обновление внешнего сервера.

Цена простой передачи JPEG — повышенный трафик по сравнению с видеокодеком и нагрузка на сервер для каждого зрителя. В WebSocket-режиме источник кодирует кадры только при активном просмотре, до 5 кадров/с, длинная сторона до 960 px, размер до 200 КиБ. Видео не хранится на диске.

## Контракт API

Все даты — ISO UTC, кроме временных числовых значений детектора. Ошибка: JSON `{ "error": "читаемое сообщение" }`. Объекты ниже — согласованные интерфейсы независимых частей реализации. Обозначение host означает сессию владельца комнаты, а не прежний hostToken. Для изменяющих запросов требуется точный Origin приложения. Интерфейс отправляет ожидаемый ID аккаунта в X-BarkOdd-User; несовпадение с cookie отклоняется, чтобы смена аккаунта в другой вкладке не меняла владельца действия. GET /api/rooms возвращает список комнат текущего владельца.

- `POST /api/rooms` `{name}` → 201 `{id,ownerId,hostToken,viewerToken}`. Требуется владелец. hostToken сохранён в форме ответа для совместимости, но больше не авторизует управление. viewerToken криптографически случайный. Имя 1–60 символов, до 100 комнат на сервер.
- `GET /api/rooms/:id` (сессия владельца или гостевой ключ) → `{id,name,createdAt,lastSeenAt,online,monitoring,sessionId,mediaTransport,lastNoiseAt,settings,eventCount,events}`. `settings:{threshold:0.06,quietMs:5000,snapshotIntervalMs:30000}`. `events:[{id,startedAt,lastNoiseAt,photoAt,hasPhoto,level}]` новые сверху. Даты без значения — null. online — heartbeat за последние 15 с; monitoring действительно только при online.
- `PUT /api/rooms/:id/settings` (host) `{threshold,snapshotIntervalMs}` → settings. threshold 0.005–0.5, interval 10000–300000.
- `POST /api/rooms/:id/heartbeat` (host) `{monitoring,sessionId,stopped?}` → `{ok:true}`. stopped:true означает окончательную остановку; временное monitoring:false не завершает сессию. sessionId — новое случайное значение при каждом новом запуске камеры, при polling не меняется.
- `POST /api/rooms/:id/events` (host) `{sessionId,episodeId,level,photo?,detectedAt?,photoAt?}` → event. episodeId ограниченный идентификатор клиента, фото `data:image/jpeg;base64,...`, не более 400 KiB decoded. Клиент передаёт реальное время обнаружения/съёмки (ISO UTC, допустимы последние 24 ч и погрешность вперёд 5 с); без дат используется время сервера. Поздние повторы не откатывают lastNoiseAt/photoAt. Сервер объединяет обновления эпизода, ограничивает частоту фото, число/срок истории. Обновления эпизода обязаны сохранять lastNoiseAt и не заменять photoAt, если фото не менялось.
- `GET /api/rooms/:id/events/:eventId/photo` (сессия владельца или гостевой ключ) → JPEG, Cache-Control:no-store. Клиент получает через авторизованный fetch и создаёт blob URL.
- `POST /api/rooms/:id/pairing` (host) → `{viewerToken}`; отзывает старый ключ просмотра.
- `POST /api/rooms/:id/qr` (host) `{viewerToken,origin}` → PNG. origin принимается только как http(s) origin, PUBLIC_URL приоритетен; QR содержит `<PUBLIC_URL>?role=viewer#room=ID&key=TOKEN` с сохранением подпути. viewerToken должен соответствовать действующему ключу.
- `GET /api/rooms/:id/stream` → WebSocket, протокол ниже. Прежние `/ice` и `/signals` удалены.
- `GET /healthz` → `{status:"ok"}`. Static index + JS + CSS embedded.

## WebSocket-протокол

- Origin должен совпадать со схемой и host `PUBLIC_URL`, либо текущего HTTP-запроса при локальном запуске. Ключи в query string и заголовке Authorization WebSocket-запроса запрещены.
- Первое сообщение за 5 секунд: `{type:"auth",role:"host"|"viewer",token?,sessionId?}`. Гостевой token даёт только роль viewer; без него проверяется cookie владельца (либо неявный владелец в none). Источник сначала успешно отправляет heartbeat с текущей сессией, затем авторизует WebSocket.
- Ответ: `{type:"ready",role,mediaTransport,clientId,iceServers?}`. clientId уникален для текущего сокета; ICE-конфигурация выдаётся только авторизованному RTC-клиенту. При переподключении источник вновь подтверждает сессию heartbeat. Источнику отправляется `{type:"viewers",count,ids,monitoring}`; зрителю — `{type:"source",online,monitoring,sourceId}`. Изменения доставляются сразу либо при проверке состояния раз в секунду.
- В WebSocket-режиме источник отправляет binary JPEG; сервер передаёт его авторизованным зрителям комнаты. Зритель не может публиковать кадры. Проверяется JPEG header, лимит 200 КиБ, размеры не более 1280 по каждой стороне и 1280×720 пикселей суммарно. Приём ограничен 5 кадрами/с с небольшим запасом для колебаний интервала.
- Лимиты: один источник, шесть зрителей на комнату, 32 ожидающих авторизации соединения на сервере; общий предел — 732 соединения, включая закрывающиеся. Очередь каждого зрителя содержит только последний кадр; медленная запись ограничена двумя секундами. Сетевые операции не держат общий mutex комнат.
- Нет сохранённого кадра для следующего зрителя. Каждая отправка проверяет действительность ключа/версии и сессии источника; отзыв ключа закрывает старые соединения на сервере. Смена сессии и временная пауза инвалидируют очередь кадров.
- `stopped:true` окончательно завершает сессию. Временное `monitoring:false` допускает восстановление того же источника после возврата микрофона. Ping/pong проверяет соединение; завершение сервера закрывает hijacked sockets.
- Ошибка: `{type:"error",status,message}` и закрытие соединения. При неверном/отозванном ключе клиент прекращает повторы. При временном обрыве повторяет через 0.5–5 секунд. Если нет новых кадров 3 секунды, зритель скрывает застывшее изображение.

## WebRTC

Подробный протокол: [дизайн двух транспортов](superpowers/specs/2026-11-06-dual-transport-design.md). В RTC-режиме binary JPEG отвергается; в JPEG-режиме signaling отвергается. Сообщение `{type:"signal",target,connectionId,signal}` сервер пересылает как `{type:"signal",from,connectionId,signal}`, проверяя роль, комнату и актуальность участников. Offer только от источника, answer от зрителя, ICE в обе стороны. Предел 64 КиБ, FIFO 64 сообщения/256 КиБ на адресата, 40 сообщений/с с burst 80.

В RTC каждую секунду сервер подтверждает список зрителей/источник, даже без изменений. Источник закрывает peers исчезнувших зрителей. Потеря WS или 6 с без подтверждения закрывает peers; это обеспечивает отзыв P2P через источник, а не только закрытие сокета зрителя. Идентификатор источника не меняется от обычного heartbeat. Временная пауза меняет отдельный rtcEpoch для отбрасывания задержанного signaling.

`web/rtc.js` создаёт только video senders. Host инициирует offer с новым connectionId; очередь candidates до remoteDescription ограничена 128, поздние promise completions проверяют generation. Декодированные кадры подтверждаются video-frame callback или счётчиком декодирования: ICE connected само по себе не означает live. Застывший кадр убирается через 3 с.

ICE задаётся `STUN_URLS` и `TURN_URLS`; `STUN_URLS=none` отключает default STUN. TURN требует shared secret или статическую пару. Shared-secret credentials живут 1 час. Клиенты с TURN обновляют контрольное соединение каждые 45 минут, получая новые credentials и перестраивая peers; это может ненадолго прервать видео. Секрет не выдаётся браузеру, внешняя доступность TURN проверяется отдельно.

## Интерфейс медиамодуля (web/media.js)

Экспорт `createMonitor({api,onStatus,onLevel,onLocalStream,onFrame,onTransport,onRemoteStream,onError})`. `api` содержит `streamURL`, `token`, методы `get(path)`, `post(path,body)`, `put(path,body)` относительно `/api/rooms/:id`; URL сохраняют внешний подпуть. `onStatus` получает `{kind,message}`; kind: idle/starting/monitoring/connecting/live/offline/error. `onLevel(value)` — 0..1, `onLocalStream` — MediaStream|null, `onFrame` — Blob|null, `onTransport` — выбранный режим, `onRemoteStream` — MediaStream|null для RTC, `onError` — Error.

Методы возвращённого объекта:

- `startHost({videoDeviceId?,audioDeviceId?,settings})`: запрашивает медиа и запускает шум/heartbeat/WS. Недоступный, отключённый или приостановленный микрофон не считается работающим наблюдением.
- `stopHost()`: останавливает захват, WebSocket и таймеры, отправляет `stopped:true`.
- `startViewer()`, `stopViewer()`: включают/выключают получение кадров, освобождают соединение и текущий кадр.
- `updateSettings(settings)`, `destroy()`: destroy освобождает таймеры, потоки, AudioContext, WebSocket и wake lock.
- `NoiseDetector` из `web/noise.js`: constructor({threshold,quietMs,snapshotIntervalMs,minNoiseMs=150}), `process(level,now)` → null либо `{episodeId,takePhoto}`. Обновление шума не чаще 1000 мс; episodeId независим от wall clock. Новый episodeId создаётся после quietMs тишины и окончания snapshotIntervalMs от более позднего из начала эпизода и последнего успешного снимка/подтверждения. `photoCaptured(now)` подтверждает успешный JPEG и затем его сохранение сервером, начиная/продлевая интервал; неудачная съёмка его не расходует. Очередь повторяет JPEG, пока ответ `/events` не подтвердит его `photoAt`. `updateSettings(settings)` меняет настройки.

Источник использует отдельный canvas для live-кадров, не пересекающийся с фото событий; одновременно кодируется один кадр, `bufferedAmount` ограничивает отправку. Очередь шумовых событий сохраняет время обнаружения и съёмки при временном отсутствии сети.

UI показывает локальное `<video>` только источнику; зрителю — `<img>` с blob URL для JPEG или отдельное `<video>` для RTC. Очередь JPEG-декодирования ограничена последним кадром, ссылки освобождаются при замене и остановке. UI регулярно получает состояние, рендерит историю и фотографии, хранит ключи в браузере. QR и перевыпуск ссылки доступны только источнику. При неизвестном ключе/комнате показана ошибка и возврат к выбору роли.

## Проверки

Go integration/race: авторизация и роли, Origin, WebSocket fanout и ограничения, отзыв ключа, завершение соединений, persistence/restart, шум+интервал, валидация JPEG, TTL/retention и неправильные данные. JS: детектор шума, состояние микрофона, события/снимки, WS lifecycle, отсутствие отправки без зрителей и ограничения кадров.

Браузерная проверка WebSocket запускается с отсутствующим `RTCPeerConnection` и искусственными camera/microphone: кадры меняются, выключение просмотра останавливает upload, mic pause/resume и отключение сети скрывают кадр, повторный запуск источника восстанавливает просмотр. Отзыв ключа закрывает прежний WebSocket даже без дальнейшего HTTP polling. Проверяется `/barkodd/`, фотографии, восстановление после ошибки загрузки и мобильная ширина. Реальная камера/микрофон и соединение через мобильного оператора отдельно обозначаются как непроверенные.

WebRTC проверяется настоящими браузерными peers: только video sender, кадры декодируются, отзыв ключа закрывает host peer даже если viewer игнорирует WS callbacks. Оба режима проходят /barkodd/, mic pause/resume и события. Перезапуск с другим MEDIA_TRANSPORT проверен без перезагрузки страниц.


## Авторизация при запуске

`AUTH_MODE=none|admin_code|multi_user` выбирает общий открытый кабинет, общий
кабинет с входом по коду или отдельные аккаунты с самостоятельной регистрацией.
Комната имеет постоянный ownerId. HTTP и WebSocket принимают сессию владельца
из HttpOnly cookie; старые host tokens управление не разрешают. Гостевой ключ
сохраняет доступ только к просмотру конкретной комнаты. Блокировка владельца
останавливает доступ и активные соединения; пароли хешируются Argon2id.
Учётные записи хранятся под DATA_DIR/auth/, сессии в памяти. Полная схема:
[режимы авторизации](superpowers/specs/2026-11-06-auth-modes-design.md).
